# Fitness Coaching PWA — Frontend Development Specification

## 1. GLOBAL DESIGN SYSTEM

### 1.1 Design philosophy

The application should feel like a professional performance/coaching platform.

Primary principles:

1. Training information must be immediately readable.
2. The athlete should reach today's workout in one tap.
3. Logging a set should require minimal interaction.
4. Coaches should be able to manage many athletes without excessive navigation.
5. Mobile is the primary athlete experience.
6. Desktop is the primary coach experience.
7. Avoid excessive decoration.
8. Use visual hierarchy rather than large amounts of text.
9. Important performance numbers should be visually prominent.
10. Every action should provide immediate feedback.

---

# 2. GLOBAL RESPONSIVE BREAKPOINTS

Use four layout states.

### Mobile

`< 640px`

* Athlete primary target.
* Bottom navigation.
* One-column layout.
* Full-width cards.
* Large touch targets.
* Minimal tables.

### Tablet

`640px – 1024px`

* One/two-column layouts.
* Collapsible navigation.
* Larger charts.
* Some tables converted into cards.

### Desktop

`1024px – 1440px`

* Coach primary target.
* Persistent sidebar.
* Two/three-column dashboard.
* Full tables.

### Large desktop

`> 1440px`

* Maximum content width.
* Do not continuously stretch cards.
* Center content around `1200–1400px`.

# 5. GLOBAL SPACING

Use a consistent spacing scale.

```text
4px
8px
12px
16px
20px
24px
32px
40px
48px
64px
```

Recommended:

* Card internal padding: `16–24px`
* Section spacing: `24–32px`
* Page horizontal padding mobile: `16px`
* Page horizontal padding desktop: `24–40px`
* Button height: `44–48px`
* Small button: `36–40px`
* Input height: `44–48px`

---

# 6. GLOBAL CARD STYLE

Cards should have:

* Moderate corner radius: `12–16px`
* Thin border
* Very subtle shadow, if any
* Consistent internal padding
* Clear header/content separation

Avoid excessive floating cards.

Use cards primarily when they group related information.

---

# 7. GLOBAL TYPOGRAPHY

Use one primary sans-serif font.

Suggested:

**Inter** or **Manrope**.

Hierarchy:

```text
Page title       28–32px / bold
Section title    18–22px / semibold
Card title       15–18px / semibold
Body             14–16px
Secondary        12–14px
Metric           28–40px / bold
```

Performance numbers should be larger than descriptive text.

# 14. SET LOGGER

The set logger must be designed for one-handed gym use.

### Components

```text
SetRow
├── SetNumber
├── WeightInput
├── RepInput
├── RPESelector
└── CompletionButton
```

### Input behavior

Weight:

```text
[-] 140 [+]
```

Reps:

```text
[-] 5 [+]
```

RPE:

```text
6  7  8  9  10
      ●
```

Avoid forcing the user to type every number.

Remember previous values and prepopulate where appropriate.

# 40. GLOBAL STATES

Every data-driven page must support four states.

## Loading

Use skeletons.

Example:

```text
████████████
██████
████████████████
```

Avoid full-screen spinners unless absolutely necessary.

---

## Empty

Example:

```text
NO WORKOUTS YET

Your coach hasn't assigned your first workout.

```

Provide the next logical action where applicable.

---

## Error

```text
Something went wrong.

We couldn't load your workout.

[ TRY AGAIN ]
```

---

## Success

Use toast/snackbar:

```text
✓ Workout saved
```

Do not interrupt the user with unnecessary modal confirmations.

# 50. The key product rule

The frontend should always prioritize **the next action**.

For the athlete:

> **What do I need to do today?**

For the coach:

> **Which athlete needs my attention?**

For progress:

> **Am I getting better?**

For the program builder:

> **What am I prescribing next?**

If every screen follows those four principles, the application will feel like a **coaching platform**, rather than just another workout-tracking app.
